# 质量验收

[English](quality.en.md) | [题库](../tests/quality/cases.json)

本项目作为原生联网的备用方案维护。新改动应证明至少一项改善：原生失败时能够完成任务、读取更省上下文、取消和退出更可靠。

## 运行

在仓库目录执行：

```powershell
npm run quality
npm run quality -- --browser
npm run quality -- --browser --live
```

单独进行有费用的 Claude Code 最小对照：`node tests/quality/claude-live.mjs --run`。默认不运行，需明确同意消耗模型额度。它通过当前用户的设置读取模型认证，只放入子进程环境，不写入仓库、不放在命令行参数。每组最多 5 轮、150 秒，CLI 预算设为每组 0.15 美元；第三方模型的 CLI 价格可能无法识别，**这个数不是第三方账单的可靠硬上限**。仅两组文档题，不加载全局 MCP，不重新注册工具。结果保存在被忽略的 `.quality/claude-live.json`。原生组只开放 WebSearch/WebFetch；本题无浏览器交互，不能当作完整 Playwright 对照。CLI 返回 success 但没有真实工具调用，也判验收失败。CLI 报价不等于实际账单。

0.14 的实测和未通过项见[本轮验收记录](quality-0.14.zh.md)。

默认仅运行本地协议/文档、请求生命周期、父进程监测测试。`--browser` 启动真实无头浏览器访问本地动态页面；`--live` 让 Node 和 Python 分别搜索固定中文姓名并读取 Python 官方文档。联网搜索显式指定免费 DuckDuckGo/Bing RSS，不使用 DeepSeek 等付费接口，不调用 Claude 模型，也不重新注册 MCP。免费站点仍可能反爬或限流。

P0 更新后，默认额外运行网络权限、重定向、Cookie 文件权限和会话隔离测试；`--browser` 也会检查强制结束测试 MCP 后真实浏览器/daemon PID 是否退出。历史白框的窗口根因仍需在症状出现时诊断。安全配置见[安全默认值](security.zh.md)。

报告输出至 `.quality/latest.md` 和 `.quality/latest.json`，目录被 Git 忽略。报告会覆盖上次结果；比较改动前后时应先复制该目录留作基线。报告可能含公开网页摘录，不包含环境变量或配置密钥。

## 如何解释

- 自动套件通过率仅表示本地断言通过，不能代表搜索相关性或答案正确率。
- 套件耗时是整套耗时，不能当单次搜索延迟；日志字符数也不能当模型输入量。
- 联网行记录每次 MCP 调用的耗时、返回文本字符数、唯一结果 URL，以及最多 4000 字符的摘录。字符数不是 Token，用量以模型服务实际记录为准。
- `returned` 表示收到非错误结果，`empty` 表示没有搜索结果，`provider_error` 表示无结果且诊断包含超时、限流或源失败，`error` 表示工具请求失败。源错误检测依赖诊断文本，是辅助标记，仍需检查 provider notes。均需要人工检查正文质量。
- 官方文档题现在直接定位 TaskGroup 等待行为；`evidence_missing` 表示检索未返回命中，会使验收命令失败，而不是把空证据计作读取成功。
- Python 或 PDF 依赖缺失必须检查跳过说明，不得算完整覆盖。默认父进程监测使用模拟 daemon；`--browser` 另跑真实 PID 退出检查，两者不可混淆。
- 恢复测试覆盖两版本地 HTTP 429、冷却期间不请求、到期后真实 MCP 请求恢复，以及受控时钟下的单个恢复试探。arXiv 自身冷却的在线到期恢复仍未实测。

## 与原生工具对照

在同一机器、网络和 Claude Code 模型下，对题库每个问题分别运行两组。A 组停用 net-tools，使用原生 WebSearch/WebFetch 与已有 Playwright；B 组临时启用 net-tools，并明确要求只用它完成测试。每题新会话，先各跑一次；有差异再重复三次。不要同时改变代理、模型和工具版本。题库长论文题没有提供 arXiv ID，要求模型先查找。

本脚本不会代替你调用 Claude Code 原生工具，因此 A 组和模型主动选工具行为均未自动测量。启用会话产生的模型和搜索费用应由操作者决定；脚本不会自动触发。

每组每题记录：

首次运行会生成 `.quality/comparison.csv`，预填两组共 16 行，状态均为未测。后续运行不会覆盖这个文件；可直接用表格软件填入审查结果。

| 字段 | 记录方法 |
| --- | --- |
| 完成状态 | 完成 / 部分完成 / 失败 / 未测 |
| 有效来源比例 | 打开并人工确认支持问题的唯一原始 URL 数 / 已审查的唯一 URL 总数；分母为零填未测 |
| 正文读取成功率 | 得到相关正文而非验证页、错误页的 URL 数 / 尝试读取的唯一 URL 数 |
| 首条有效来源耗时 | 从提交问题到首个经核查有效来源的秒数；没有有效来源填失败 |
| 总耗时 | 同样起点到任务结束 |
| 输出量 | 工具文本字符数；有实际 usage 时另记 Token，不估算换算 |
| 来源证据 | 最终 URL、支持结论的摘录、网页章节或 PDF 页码 |
| 后台残留 | 前后进程快照中属于本次任务且尚存的 CLI/daemon/浏览器；不以所有 Chrome 总数判断 |
| 费用 | 实际账单/usage；无法取得填未测 |

不因 HTTP 200、引用数量多或页面可打开就判定来源可信。人物题不得预设身份；必须检查同名歧义。公式、扫描 PDF 和登录页面另记能力边界。

## 发布门槛

搜索源按配置顺序执行。有后续来源时，当前来源最多分配剩余总预算的均份，且不超过 8 秒；最后一个来源可以使用剩余时间。这样给后续来源留下机会，但不能保证所有站点都能在预算内响应，也不自动改变结果排序。Python 每个来源使用独立截止时间，并共享父请求的取消状态。

后续修复：Python 的 Bing RSS 优先使用本机 curl，与 Node 采用相同传输工具；未安装 curl 时保留 urllib。一次相同 Windows 网络条件下的复测中，Node 约 8.9 秒、Python 约 11.1 秒各返回 3 条姓名搜索链接；Python 在 DuckDuckGo 超时后成功取得 Bing RSS 结果。两版官方文档读取、本地回归均通过。这证明本轮回退路径可用，不是准确率或普遍性能提升的保证，也未自动审查链接可信度。

首轮 Windows 实测发现：两版本地回归和真实浏览器测试通过；免费搜索源下，Node 中文姓名查询约 16.6 秒得到 3 条链接，Python 同题耗尽 20 秒预算，官方 Python 文档读取两版均返回正文。这只是当前网络下的单机观察，未审查所有结果来源，也没有原生工具对照，不能据此宣称准确率或速度提升。测试还暴露并修正了 Python 把 TimeoutError 改写成“子进程不可用”的诊断错误；免费搜索超时本身仍待优化。

本地套件失败时不发布。跳过项必须披露。搜索质量改善需附人工来源核查和对照记录；没有测量就保留“未测”，不要填零或宣称提升。若 net-tools 没有在对照中补足缺口，继续保持按需停用。
